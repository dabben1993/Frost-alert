# Candidate Digest: MET Norway / Yr.no API (api.met.no, Locationforecast 2.0)

Research scope: hobby frost-alert automation checking overnight low temperatures for a Sweden-based user. Sources are primary (api.met.no / docs.api.met.no) where possible, supplemented by ecosystem (Home Assistant) and independent Swedish academic accuracy comparisons.

## Claims

- Locationforecast/Yr data is free to use, including commercial use, with no API key and no pricing tier for high-volume users — the service is explicitly non-commercial and taxpayer-funded — source: MET Weather API FAQ, "Do you have a pricing model for high-volume sites?", https://docs.api.met.no/doc/FAQ.html, published: undated, accessed: 2026-09-12, confidence: high, class: pricing
- Data is licensed under NLOD 2.0 / CC BY 4.0, requiring attribution to "MET Norway" as the data source plus a link to the license/source — source: MET Weather API Licensing page, https://api.met.no/doc/License (corroborated by met.no "Licensing and crediting", https://www.met.no/en/free-meteorological-data/Licensing-and-crediting), published: undated (met.no page last modified 2021-02-01), accessed: 2026-09-12, confidence: high, class: pricing
- All requests must send an identifying User-Agent (app/domain name plus contact email or website); missing, generic, or "banned" User-Agents (examples given: okhttp, Dalvik, Java) receive a 403 Forbidden — source: MET Weather API Locationforecast documentation, https://api.met.no/weatherapi/locationforecast/2.0/documentation, published: undated, accessed: 2026-09-12, confidence: high, class: integration
- Traffic over 20 requests/second per application (aggregated across all users of that app) requires a special agreement with MET; exceeding limits or breaching identification rules leads to HTTP 429 throttling and, for repeated/deliberate abuse, a permanent ban — source: MET Weather API Terms of Service, https://api.met.no/doc/TermsOfService (corroborated by MET Weather API Status Codes doc, https://api.met.no/doc/StatusCodes), published: last revised 2020-06-26, accessed: 2026-09-12, confidence: high, class: pricing
- For a low-volume personal automation (a handful of requests per day/hour), the practical constraints are: identify via User-Agent, respect the `Expires`/`Last-Modified` cache headers, avoid hitting the API on-the-hour (add jitter), and use max 4 decimal places on lat/lon (5+ decimals returns 403 on newer products) — source: MET Weather API Terms of Service, https://api.met.no/doc/TermsOfService, published: 2020-06-26, accessed: 2026-09-12, confidence: high, class: integration
- Locationforecast/2.0 covers any location on Earth for up to 9 days ahead, using a global ECMWF-based model blended with higher-resolution, more-frequently-updated models for the Nordic and Arctic region (MET's stated priority area); non-Nordic areas get the coarser global-only data — source: MET Weather API Locationforecast data model docs, https://docs.api.met.no/doc/locationforecast/datamodel.html, published: undated, accessed: 2026-09-12, confidence: high, class: coverage
- Sweden falls within MET's "Nordic" priority region, so it receives the more frequently updated, higher-resolution forecasts (not just the coarse global fallback); the `next_1_hours` short-range/high-res period variable is explicitly only available in this higher-resolution short-range forecast — source: MET Weather API Locationforecast data model docs, https://docs.api.met.no/doc/locationforecast/datamodel.html, published: undated, accessed: 2026-09-12, confidence: high, class: coverage
- Temperature-forecast accuracy is sensitive to the elevation parameter supplied in the request; if omitted, MET falls back to a 1km-resolution global topography dataset (GMTED2010) and adjusts air temperature via a standard adiabatic lapse rate — meaning omitting elevation for a specific garden/property could measurably skew frost-relevant low-temperature forecasts — source: MET Weather API Locationforecast data model docs, https://docs.api.met.no/doc/locationforecast/datamodel.html, published: undated, accessed: 2026-09-12, confidence: high, class: accuracy
- Location must be specified as latitude/longitude (EPSG:4326); MET's own HOWTO recommends GeoNames or OpenStreetMap Nominatim for converting place names to coordinates, since Locationforecast itself has no geocoding — source: Locationforecast HOWTO, https://docs.api.met.no/doc/locationforecast/HowTO.html, published: undated, accessed: 2026-09-12, confidence: high, class: integration
- Response format is GeoJSON (`compact` or `complete` endpoints), with UTC timeseries, an OpenAPI/Swagger schema, and period-aggregate blocks (`next_1_hours`, `next_6_hours`, `next_12_hours`) alongside instantaneous values — documentation is detailed and primary-source (own datamodel, JSON-format, and OpenAPI reference pages) — source: MET Weather API "General point forecast JSON format" doc, https://api.met.no/doc/ForecastJSON, published: undated, accessed: 2026-09-12, confidence: high, class: integration
- No SLA or delivery guarantee is offered for any user, free or otherwise; MET explicitly states it cannot offer higher service levels to paying customers because it is a non-commercial public service (recognized by the UN Digital Public Goods Alliance as a "digital public good") — source: MET Weather API FAQ, https://docs.api.met.no/doc/FAQ.html, published: undated, accessed: 2026-09-12, confidence: high, class: reliability
- Third-party client libraries exist and are actively maintained for Locationforecast/2.0, e.g. Python packages `metno-locationforecast` (github.com/Rory-Sullivan/metno-locationforecast) and `yr-weather` (github.com/ZeroWave022/yr-weather, published on PyPI, typed/documented); MET Norway's own client-library page disclaims responsibility for third-party libraries and warns some are broken or built against the deprecated v1.9 endpoint — source: api.met.no Client Libraries doc, https://api.met.no/doc/ClientLibraries, published: undated, accessed: 2026-09-12, confidence: medium, class: integration
- The API is the default/official weather integration in Home Assistant (used by roughly 83% of active Home Assistant installations as of the currently published integration docs), requires no API key, and is described there as "free" and subject to MET's fair-use TOS — a strong ecosystem/reputation signal for real-world hobbyist reliability — source: Home Assistant "Meteorologisk institutt (Met.no)" integration docs, https://www.home-assistant.io/integrations/met, published: undated (live/current doc), accessed: 2026-09-12, confidence: medium, class: reliability
- A documented real-world integration pitfall: Home Assistant users report inaccurate temperature forecasts traced to an incorrectly set "elevation" field in the Met.no integration config (independent from the system-wide elevation setting), which several community threads had to troubleshoot — corroborates the primary-source claim above that elevation strongly affects temperature accuracy — source: Home Assistant Community forum threads on Met.no elevation/sunrise issues, https://community.home-assistant.io/t/why-are-the-sunrise-and-sunset-times-wrong/676892 and https://community.home-assistant.io/t/next-rising-and-next-setting-still-shows-appr-2-minutes-too-late-gmt-1-central-europe-slovenia/566922, published: undated (active/ongoing threads), accessed: 2026-09-12, confidence: medium, class: reliability
- Independent Swedish academic comparisons of short-range (0–24h) 2m temperature forecasts found MET Norway/Yr accuracy broadly comparable to Sweden's own national service SMHI: a 2018 Uppsala University study across 22 Swedish stations found met.no had "somewhat higher" hit-rate than SMHI for most stations (though both institutes were less accurate in February/winter, in the north, and in mountainous terrain than in spring); a separate Uppsala thesis comparing SMHI vs YR 24h forecasts at 13 Swedish stations found differences "generally small and rarely statistically significant" for temperature (larger, more meaningful differences appeared for wind speed, where Yr tended to do better in mountainous/high-altitude terrain) — source: Uppsala University thesis, "Comparison of Short-Range Temperature Forecasts from SMHI and the Norwegian Meteorological Institute," DiVA, http://urn.kb.se/resolve?urn=urn%3Anbn%3Ase%3Auu%3Adiva-383449; and Uppsala University thesis, "Jämförelse av SMHI:s och YR:s 24-timmarsprognoser för temperatur och vindhastighet," DiVA, http://urn.kb.se/resolve?urn=urn%3Anbn%3Ase%3Auu%3Adiva-577046, published: undated (not confirmed by direct fetch; catalog metadata not opened), accessed: 2026-09-12, confidence: medium, class: accuracy
- An independent hobbyist blog analysis comparing 24h-ahead YR vs SMHI temperature forecasts for Stockholm (Bromma) found near-identical accuracy: correlation ~0.98 for both, median absolute error of 1°C for both, RMSE 2.37°C (SMHI) vs 2.51°C (YR) — i.e. no dramatic accuracy gap, SMHI marginally better in this single-city sample — source: "Follow the Data" blog, "Temperature forecast showdown: YR vs SMHI," https://followthedata.wordpress.com/2017/07/21/temperature-forecast-showdown-yr-vs-smhi/, published: 2017-07-21, accessed: 2026-09-12, confidence: low (single older blog post, well outside the 12-month landscape-claim freshness bar, but directionally consistent with the two academic theses above), class: accuracy

## Leads

- MET Norway's Frost API (a separate product, historical/observed climate data, e.g. github.com/ArcticPuffin/frost_api_metno) could be used to backtest a frost-alert threshold against real historical overnight-low events in Sweden — not itself the forecast source, but worth checking as a validation companion.
- The 2018 Uppsala thesis and the second (undated/possibly more recent) Uppsala DiVA thesis on SMHI-vs-YR forecasts were only read via search snippets, not fetched directly; the full PDFs likely contain per-station and per-season breakdowns (including winter/cold-season performance) that would be directly relevant to a frost-alert use case and are worth reading in full.
- Home Assistant's Met.no integration GitHub "known issues" and "feature requests" pages (linked from https://www.home-assistant.io/integrations/met) were not opened; they likely contain more granular, dated reports of accuracy or reliability problems from real users, including any in Nordic countries.
- MET Norway runs a mailing list and RSS feed for API change/deprecation announcements (referenced in the Terms of Service); subscribing would be the recommended way to track breaking changes for a long-running hobby automation.
- Third-party Python wrapper `yr-weather` also exposes MET's Sunrise and Textforecast products, which could be useful extras (e.g. combining sunrise/sunset with frost timing) beyond the core Locationforecast data needed here.

## Could not find

- No independent accuracy study specifically isolating overnight/nighttime minimum-temperature forecast skill (as opposed to generic 24h point-in-time temperature accuracy) for Sweden or Scandinavia — the located studies compare general 0–24h temperature forecasts, not frost-specific overnight lows.
- No developer blog posts, GitHub issues, or forum threads describing a from-scratch (non-Home-Assistant) hobby integration of api.met.no specifically for a frost/plant-protection alert use case.
- No accuracy/landscape comparison published within the last 12 months; the two academic theses and the blog comparison found are from 2017–2018 and an unconfirmed/uncertain-dated thesis, all outside the requested freshness bar for landscape claims — this should be treated as a gap, not a settled recent verdict.
- Could not confirm the exact horizontal grid resolution of the global (ECMWF-sourced) portion of the model with full certainty — the primary data-model documentation stated "approximately 9 [km?]" but the retrieved text was truncated at that point; not included as a firm claim.
- No explicit statement found (primary or secondary) of a hard daily/monthly request quota — MET's terms describe only a rate ceiling (20 req/s per application) and fair-use/traffic-shaping expectations, not a fixed quota number.
