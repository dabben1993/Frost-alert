- (lock) Single-user personal automation, not a hosted multi-tenant service. No accounts, no handling other people's keys/data. But config (location, temp scale/threshold, notification channel) must be set via an intuitive setup flow (e.g. interactive CLI wizard or simple config UI) - never requires editing code - so a friend or future-you-after-moving can reconfigure it themselves.
- (lock) Trigger is forecast-based, not live temperature. Escalating check cadence: first warning from 24hr-ahead forecast (awareness), then re-checks narrower windows (8hr, then 6hr, then 4hr) as the event approaches, each re-alerting if still relevant. Escalation for a given cold event stops early if the user acknowledges plants are moved to overwintering.
- (decision) Trigger is forecast-based, not live-reading-based. Escalating check cadence: first alert at 24h-out forecast (awareness), then re-check and re-alert at shorter windows (12h, then 8/6/4h - exact steps TBD) if user hasn't acknowledged. Escalation stops once user confirms plants are moved to overwintering.
- (crack) Escalating alerts + user acknowledgment ('plants moved to overwintering') means the channel can't be pure one-way push - needs a reply/button/interaction mechanism. This narrows channel choice significantly (favors Telegram bot / WhatsApp / clickable web link over plain SMS or email).
- (lock) Overwintering ack is a one-time seasonal toggle (not nightly snooze). Flipping it off suspends all alerts until user turns it back on (e.g. in spring).
- (decision) Hosting must not depend on a personal always-on device (none available). Prefer cost; if unavoidable, cheapest viable option. Specific platform (e.g. GitHub Actions cron, serverless scheduler) deferred to research phase.
- (lock) Alert threshold is a user-set number (per-user config), not hardcoded to 0C. Default should build in a safety margin above literal freezing (e.g. ~3C) to account for forecast error and radiative frost, tunable down over time. Applies in the user's chosen temperature scale.
