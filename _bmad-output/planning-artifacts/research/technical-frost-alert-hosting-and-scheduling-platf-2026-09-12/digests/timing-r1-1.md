**GitHub Actions — setup/maintenance burden ("write once and forget"?)**

**Cloudflare Workers Cron Triggers — implementation/setup complexity & silent-failure debugging**

- CLAIM: Official Cloudflare docs state Cron Trigger changes (add/update/delete) "may take several minutes (up to 15 minutes) to propagate to the Cloudflare global network," and it "can take up to 30 minutes before events are displayed in Past Cron Events when creating a new Worker or changing a Worker's name" — meaning testing/debugging a newly configured schedule has an inherent, undocumented-feeling lag. | SOURCE: Cloudflare Docs (official) | URL: https://developers.cloudflare.com/workers/configuration/cron-triggers/ | PUB_DATE: undated (living doc) | ACCESSED: this session | CONFIDENCE: high | CLASS: implementation
- CLAIM: Cloudflare Workers Cron Triggers have no automatic retry on a failed/timed-out `scheduled()` invocation and no built-in failure-alert mechanism (email/webhook); a failed run is simply lost until the next scheduled tick, and the only native way to notice is checking the dashboard's Cron Events / Workers Logs or observing a downstream break. This is asserted independently by three unrelated third-party scheduler vendors (each pitching an alternative/wrapper product), and is consistent with the `controller.noRetry()` opt-out field documented officially (implying no default retry guarantee developers can rely on). | SOURCE: crontap.com, runhooks.app (x2), cronalert.com, cross-checked against Cloudflare Docs | URL: https://crontap.com/blog/cloudflare-workers-cron-minute-limit ; https://runhooks.app/blog/cloudflare-workers-cron-triggers-limits/ ; https://cronalert.com/blog/cloudflare-cron-triggers-monitoring ; https://developers.cloudflare.com/workers/configuration/cron-triggers/ | PUB_DATE: 2026 (per site self-reference "as of 2026") / official docs undated | ACCESSED: this session | CONFIDENCE: medium (claim corroborated by 3 independent advocacy/marketing sources selling a competing product — real signal, but all commercially motivated to emphasize this gap, so treat magnitude/framing with caution rather than the core fact) | CLASS: implementation
- CLAIM: Free plan is capped at up to 3 Cron Triggers per Worker (Paid plan: up to 5), with a 1-minute minimum interval on both — a real ceiling relevant to a multi-check-per-day personal scheduling need, though likely sufficient for "a few times per day" use. | SOURCE: Runhooks blog | URL: https://runhooks.app/blog/cloudflare-workers-cron-triggers-limits/ | PUB_DATE: 2026 (self-dated "2026 Reference") | ACCESSED: this session | CONFIDENCE: medium (single vendor source, but numbers align with generally known Workers limits structure; not independently re-verified against Cloudflare's own limits page in this session) | CLASS: landscape
