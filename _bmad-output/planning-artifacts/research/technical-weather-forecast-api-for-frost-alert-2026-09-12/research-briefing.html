Executive summary

Verdict

Primary: Open-Meteo. Free, no key, hourly to 16 days, blends 30+ models including a 1 km Nordic model covering Sweden, free companion geocoding API. high confidence on integration/cost, medium on accuracy signal (inferred, not independently benchmarked).

Fallback: MET Norway / Yr Locationforecast. Same lat/long input, no key, no cost, long drama-free operating history — pairs cheaply to hedge Open-Meteo's documented outages.

Cut: OpenWeatherMap (hard-gate failure — hourly data needs a paid tier requiring a credit card). Not recommended as primary: SMHI (verified breaking API change in March 2026 despite being Sweden's own national service).

The most important finding of this research run is a negative one: nobody — not SMHI, not MET Norway, not any commercial vendor, not academia — publishes a Sweden-specific, overnight-minimum-temperature-specific accuracy benchmark. Two full research rounds, in English and Swedish, across institutional, academic, and commercial sources, could not close this gap. This directly validates the project's decision to use a non-zero, tunable safety margin rather than trusting any provider's raw forecast to the degree — radiative-cooling (clear, calm) nights are structurally the hardest case for every model family, including one MET Norway itself documents failing by 14°C in a real 2024 case [21].

Requirements frame

Sourced from the project brief, not from web research — requirements are set by the project, never by search results.

Hard gates

  • Free or near-$0, no credit card required for the free tier
  • Hourly (or near-hourly) forecast data at least 24h out, ideally further
  • Accepts arbitrary locations directly or via free/low-friction geocoding, so a friend elsewhere can self-configure
  • Exposes overnight low / minimum temperature, not just a daily high

Weighted preferences

  1. Accuracy signal for Sweden, and overnight lows specifically
  2. Long-term free-tier sustainability for an unattended hobby workload
  3. Ease of integration, especially friend-friendly location input

Candidate screen

Seven candidates researched in round 1: SMHI, Open-Meteo, MET Norway/Yr, OpenWeatherMap, WeatherAPI.com, Tomorrow.io, Visual Crossing.

Cut for hard-gate failure: OpenWeatherMap — no-card free tier caps resolution at 3-hour steps; true hourly needs the paid "One Call API 3.0", which requires a credit card [22][23].

Finalists screened through: Open-Meteo, MET Norway/Yr, SMHI, Visual Crossing, WeatherAPI.com (weakest finalist — shortest horizon, mid/last-place accuracy signal [25][26]).

Cut to a footnote: Tomorrow.io — only 500 req/day with a 5-day horizon and 1 monitored location [29][30], self-contradicting rate-limit docs [41], no confirmed EU region [34]. Visual Crossing dominates it on every axis that matters here.

Evidence per criterion — Integration & location input

This dimension carries real weight: the brief requires a friend elsewhere to self-configure their location without touching code.

  • Visual Crossing and WeatherAPI.com are most friend-friendly — both accept free-text address/city/postal directly, geocoding internally [33][27].
  • Open-Meteo and OpenWeatherMap need a separate but free, no-extra-key geocoding call [13][24].
  • SMHI and MET Norway take lat/long only; both point to OpenStreetMap Nominatim, which caps at 1 req/sec — fine since geocoding only happens once at setup, then is cached [19][38].
  • MET Norway accuracy trap: temperature uses a lapse-rate correction from the elevation you supply; omitting it falls back to a coarse 1 km global topography dataset, and real users have hit measurably wrong forecasts from this [20].
  • SMHI has no official SDK — all community libraries were rewritten only in the weeks after the March 2026 breaking change and have no track record yet.

Evidence per criterion — Accuracy for overnight lows (the central, unresolved question)

No independently verified, Sweden-specific, minimum-temperature-specific accuracy benchmark exists for any candidate, despite this being the single most heavily researched question in this run (round 1 across all candidates, then a dedicated round-2 pass in English and Swedish, academic and institutional).

  • SMHI runs a continuous, public verification program (±2°C hit-rate by county/month) [5][6], but it's general, not minimum-temperature-specific, and self-evaluated. SMHI stopped issuing agricultural frost warnings in 2009 [7].
  • MET Norway's 2024 verification report documents, as a named recurring problem, a positive-bias failure on cold radiative nights: one case forecast −20°C against an observed −34°C [21] — a single case study, but the most concrete Nordic-domain evidence found of exactly this failure mode.
  • Two dated (2017–2018) but mutually corroborating Swedish academic comparisons found SMHI and MET Norway/Yr roughly equivalent on general temperature accuracy [8][9].
  • It is well-established meteorological science that radiatively-cooled nights are structurally harder to forecast than advective ones [36] — a 2025/2026 preprint on ML post-processing cites this same limitation as its motivation [37].
  • Design implication: this gap is itself the strongest argument for a tunable safety margin above literal freezing, rather than trusting any provider's raw forecast to the degree.

Quota size is not a differentiator for a single-user, once/twice-daily check — every finalist has far more headroom than needed. The differentiator is operational stability: SMHI's recent breaking change and WeatherAPI's shrinking-limits history are yellow flags; MET Norway's long, boring, drama-free history is a green flag; Open-Meteo's outages are real but manageable with a fallback.

Cross-dimension insights

  • The accuracy gap and the sustainability dimension point the same direction: since no provider is demonstrably more accurate for this use case, the tie-breaker should be operational stability and integration ease — where Open-Meteo and MET Norway pull ahead of SMHI despite its home-turf appeal.
  • The "arbitrary locations for a friend" requirement and the "no always-on device" hosting constraint compound: a geocode-once-and-cache pattern fits naturally with a stateless, scheduled job — carry this into the hosting/architecture research and the setup-wizard design.
  • MET Norway's elevation pitfall and the universal "radiative cooling is hard" finding both validate the same mitigation: the safety-margin design already locked into the project brief is doing real, evidence-backed work.

Contrary evidence

Red-team pass was not run for this session (red_team = off, not raised at the plan gate). The "Could not find" sections within each candidate digest serve as the honest-gap record instead.

Recommendations

  1. Use Open-Meteo as the primary forecast source. No key, no cost, hourly to 16 days, free geocoding companion, best-documented integration surface [10]–[15]. high on integration/cost; medium on "best accuracy signal for Sweden" (inference, not a verified ranking).
  2. Add MET Norway's Locationforecast as an automatic fallback when Open-Meteo is unreachable. Same input shape, no key, no added cost [16]–[19]. Pass elevation explicitly to avoid the documented accuracy pitfall [20].
  3. Do not build against SMHI as primary or sole source, despite it being Sweden's own service. Its breaking API change is independently verified [1][2][3][39]; a possible second retirement (Mesan2gv2, unconfirmed) would upgrade this to a pattern. Remains a reasonable secondary cross-check.
  4. Cut OpenWeatherMap entirely — free/no-card tier cannot deliver hourly resolution [22][23].
  5. Feed the unresolved accuracy question into the escalation-cadence and threshold design — keep the safety margin user-tunable; treat the 24h-out check as a coarse early warning, tightening only as shorter-window checks approach.

Open questions

  • unverified No Sweden/Nordic overnight-minimum-temperature accuracy benchmark exists anywhere. A DIY approach using Open-Meteo's own "Previous Runs"/"Historical Forecast" APIs to log predicted-vs-actual overnight lows for one winter would be more useful than any published study, and doubles as tuning data for the safety margin.
  • SMHI's SNOW1gv1 docs could not be read directly this session (JS-rendered SPA) — all structural claims are secondhand via a GitHub issue quoting the docs. Verify with a JS-capable fetch before implementation.
  • unverified A lead suggests SMHI's Mesan2gv2 analysis API may be scheduled for retirement around November 2026 — not independently confirmed. Check before committing to any SMHI-based fallback.
  • Open-Meteo's exact models= parameter value for forcing the Nordic (MET Norway-sourced) model was not confirmed — verify against the live API before implementation.
