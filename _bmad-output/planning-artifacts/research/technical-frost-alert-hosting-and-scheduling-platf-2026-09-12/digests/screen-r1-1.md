### Leads

- The GitHub "60-day auto-disable" note was found phrased specifically under public-repo framing in the docs snippet retrieved; worth double-checking in a follow-up whether it also applies identically to private repos (the retrieved snippet cluster wasn't 100% clean on this distinction).
- The dev.to claim of private-repo `schedule` being disabled on GitHub Free deserves one more targeted check (e.g. a GitHub Community Discussions thread or GitHub Support statement) since it directly contradicts official billing docs — if true, it would matter a lot for a single-user project likely using a private repo.
- Cloudflare's "noRetry" field origin (is there ANY production-level automatic retry for a failed `scheduled()` invocation, or is the vendor-blog "no retry" claim accurate?) was not resolved by official docs — a targeted search of Cloudflare Community forums or the Workers changelog could resolve this.
- Cloudflare's default cron timezone is UTC only (no per-trigger IANA timezone support was mentioned in official docs), unlike GitHub Actions which explicitly supports IANA timezones per schedule entry — worth flagging as a functional difference relevant to "hour-offsets before a forecast cold night" scheduling if local time matters.
- No evidence surfaced (in this budget) of recent pricing/free-tier changes to either platform in the last few months — worth a dated changelog check for both GitHub Actions billing and Cloudflare Workers pricing if long-term stability is decision-critical.

### Could not find

- A second independent, dated source corroborating (or refuting) the claim that GitHub Free personal accounts disable `schedule` cron on private repos — only one uncorroborated community blog post found; official docs are silent on any such restriction.
- Any official Cloudflare documentation directly and explicitly stating production retry behavior (or lack thereof) for a failing/timing-out `scheduled()` handler — only inferred from vendor blogs with a commercial interest in alternative schedulers.
- A dated GitHub changelog/blog entry quantifying "how bad" the cron delay actually is in practice (e.g. typical minutes of delay, frequency) — official docs confirm the phenomenon qualitatively but give no numeric/empirical delay data within this session's budget.
